## 1. What the project is today

Two products in one repository:

| Part | Path | What it is |
| --- | --- | --- |
| Browser app | `index.html` | Single-file WebGL2 two-oscillator XY oscilloscope. ~2400 lines of HTML/CSS/JS/shaders. Optional Web Audio, presentation mode, phase modulation, PNG export. |
| Android app | `mobile/` | Expo / React Native port of the same oscilloscope, ~1265 lines TS+TSX. React Native Skia canvas, touch controls, PNG share sheet. Pure-TS music model with unit tests. |

The Android app is the one that would go on Play. The browser app is currently
its behavioral reference.

The app is fully offline: no network code, no analytics, no ads, no permissions,
no account. That is a genuine strength for Play review (trivial Data safety
declaration, nothing to break) and the plan deliberately protects it.

### External requirements that apply right now (checked 2026-09-24)

- **Target API 36 is already required and already met.** Since 2026-08-31, new
  apps and updates must target Android 16 / API 36. The current stack targets 36
  by default, so no SDK upgrade is needed to be compliant. (Extensions to
  2026-11-01 exist if needed.)
- **New personal Play accounts (created after 2023-11-13) must run a closed test
  with at least 12 testers opted in continuously for 14 days** before the
  Production track unlocks. This is calendar time you cannot compress.
- **Google Play requires an Android App Bundle (`.aab`) for new apps**, signed
  with a real upload key, enrolled in Play App Signing. An APK alone is not a
  submission path.
- **Data safety form is mandatory for every app.**
- **Provide a privacy policy URL** and an in-app policy link. An offline app is
  not exempt from Play's User Data policy. Describe local settings, generated
  PNGs and user-initiated sharing accurately, including third-party SDK behavior.
- **Android 16 disables the edge-to-edge opt-out** for apps targeting API 36.
  Safe-area handling is now mandatory, not cosmetic (see 3.2a).
- **Predictive back is on by default** for API 36 targets on Android 16 devices;
  `onBackPressed` and `KEYCODE_BACK` are no longer delivered. A manifest opt-out
  still exists but is explicitly a temporary migration path.
- **Android developer verification** (registering Play apps, linked profiles,
  verifiable information) is effective **2026-09-30** — six days after this
  plan. Applies to Play distribution and to sideloaded builds on certified
  devices.
- Confirm any trader/contact-information requirements shown by Play Console
  for the chosen countries. Do not infer Play availability rules from Apple's
  separate App Store trader policies.

## 3. Initial findings (track completion in the progress update)

### 3.1 Hard release blockers

**a) The release build is signed with the debug key.**
A fresh `npx expo prebuild` generates `android/app/build.gradle` containing:

```gradle
buildTypes {
    debug   { signingConfig signingConfigs.debug }
    release {
        // Caution! In production, you need to generate your own keystore file.
        signingConfig signingConfigs.debug
        ...
    }
}
```

Both `assembleRelease` and `bundleRelease` therefore produce debug-signed
artifacts, which Play rejects. This needs a real upload key wired in.

**b) There is no AAB build path at all.** `package.json` has no `build:aab`
script, and the project's own release doc states the finish line is
`gradlew assembleRelease` (an APK). That is the wrong artifact for Play.

**c) `android/` is gitignored, so anything edited by hand there is silently lost
on the next prebuild.** Signing, native debug symbols, and minification must be
expressed as config plugins (or an EAS build config), not as manual edits.

**d) No app identity assets.** `app.json` declares no `icon`, no
`android.adaptiveIcon`, no splash config, no `assetBundlePatterns`, and no
`android.versionCode`. Consequences: a default Expo launcher icon, and a
`versionCode` of 1 with no version discipline — every Play upload needs a
strictly increasing `versionCode`.

**e) The application ID is the permanent identity once published.** It is
`com.icalchemy.xyoscilloscope`, chosen 2026-09-24. Play does not allow changing
it; changing it later means a brand-new app with no install migration.

**f) No privacy policy, no store listing, no Data safety declaration, no content
rating, no tester track.** All required before the first upload.

### 3.2 Bugs and quality problems (source review, not device-verified)

**a) Android safe areas are not handled at all.** `mobile/App.tsx` uses
`SafeAreaView` from `react-native`. In RN 0.81 that component is literally:

```js
const SafeAreaView = Platform.select({
  ios: require('./RCTSafeAreaViewNativeComponent').default,
  default: View,
});
```

i.e. a plain `View` on Android, and RN marks it deprecated.
`app.json` sets `edgeToEdgeEnabled: true`, SDK 54 defaults it on, and Android 16
removes the opt-out for API 36 targets. So the header can render under the status
bar, bottom content can sit under the gesture/3-button nav bar, and the
`OptionModal` bottom sheet has no bottom inset padding at all.
Fix: add `react-native-safe-area-context`, wrap in `SafeAreaProvider`, pad by
insets.

**b) The animation loop re-renders React on every frame.**
`useAnimationTime` keeps time in `useState` and calls `setTime` inside
`requestAnimationFrame`, and the hook is called from `Visualizer`. Every frame
re-renders the Skia subtree and re-runs the `useMemo` that builds **5 Skia paths
of up to 2200 samples each** (≈11,000 `lineTo` calls/frame) plus 96 circles.
This is a smoothness and battery problem in an app whose entire product value is
a smooth trace. The repository's own conversion doc claims the opposite
("animation time is kept outside normal React state") — the code does not match
the doc.

**c) Two dead controls.** `Export scale` and `Export samples` are live in the UI
and in state, but `capturePngBase64` just snapshots the on-screen canvas and
ignores both. The sliders change nothing.

**d) Touch targets below the platform minimum.** Segmented control buttons
38 px, option rows and modal triggers 42 px, color swatches 42 px, versus the
48 dp Material guidance. The visualizer is the first thing on screen, so this is
easy to fix while touching the layout.

**e) Accessibility is nearly absent.** Three `accessibility*` props in the whole
mobile app. Sliders and swatches have no labels, no roles, no selected-state
announcement.

**f) Predictive back is opted out, not migrated.** `app.json` sets
`android.predictiveBackGestureEnabled: false`, which is a documented temporary
escape hatch. The app relies on RN `Modal`'s `onRequestClose` to close pickers
on back — precisely the mechanism that breaks when predictive back is enabled
and `KEYCODE_BACK` stops being dispatched. Fine for 1.0 with the opt-out, but it
needs a regression test and a migration task.

**g) Release build is not optimized.** The template defaults
`android.enableMinifyInReleaseBuilds` to false, so R8/shrinking is off.
`expo-build-properties` can flip it, but it must be tested for R8/reflection
breakage with Skia, Reanimated and Worklets before it ships.

**h) No native debug symbols.** `ndk.debugSymbolLevel` is unset, so Play's
Android vitals cannot symbolicate native crashes — a real problem for a
Skia/Hermes app. Note that `expo-build-properties` (SDK 54) does **not** expose
`debugSymbolLevel`; this needs a small local config plugin.

### 3.4 Web → mobile feature gaps

Present in `index.html`, absent from `mobile/`:

- audio (optional, off by default, starts on user gesture)
- phase modulation (`0.001`–`0.1` Hz Y-phase cycling)
- presentation mode (fullscreen scope with live X/Y freq + amp controls)
- inline `i` help tooltips on controls

### 3.5 Improvement backlog beyond the release

Ordered by value per unit of risk, all post-1.0:

1. **Presets and state persistence.** The app remembers nothing; a scope app
   whose users build a tone and then lose it on rotation/process death is missing
   its core loop. Local-only storage keeps the Data safety declaration clean.
2. **Audio parity.** The browser app already has the design (two soft-clipped
   sine-like oscillators, user-gesture gated). This is the feature most likely
   to justify a second install.
3. **Note picker UX.** 108 notes in one flat scrolling sheet. Grouping by octave
   or an on-screen keyboard is the obvious improvement.
4. **Landscape / tablet layout.** `orientation: default` and `supportsTablet: true`
   promise landscape and tablets, but the layout is a single portrait column.
5. **Frame-time readout.** The web app shows live renderer stats; mobile shows
   only "Live samples".
6. **Settings reset / share-a-preset link.**
7. **Live wallpaper** — a natural fit for a Lissajous scope, but a large project
   (service, rendering lifecycle, battery policy). Explicitly not for 1.0.

## 5. The plan

Rough effort in engineering hours, single developer, excluding the 14-day
calendar gate.

### 5.0 Phase 0 — identity and decisions (1–2 h, blocks the upload)

1. Settle decisions 1–3, 9. Update `mobile/app.json` name/slug/description and
   `android.package` accordingly.
2. Establish a version policy: `version` for humans, `android.versionCode`
   monotonic integer, bumped once per upload. Add a one-line `CHANGELOG.md`.
3. Add the secret-exclusion lines to `mobile/.gitignore` *before* a keystore
   exists: `*.jks`, `*.keystore`, `keystore.properties`, `credentials.json`,
   `.env*`, `google-services.json`.

**Done when:** `app.json` carries the final name, package, `versionCode: 1`, and
`expo config --type public` prints the intended identity.

### 5.1 Phase 1 — release-blocking engineering (12–20 h)

Ordered by dependency. Each item has an acceptance test; see section 6 for the
evidence each one needs.

1. **Reproducible release signing.** Add `expo-build-properties` and one local
   config plugin (e.g. `mobile/plugins/withAndroidRelease.js`) that:
   - reads `android/keystore.properties` (gitignored) and adds a `release`
     signing config, and
   - sets `ndk { debugSymbolLevel 'FULL' }` on the release build type.
   Register both in `app.json`'s `plugins`. Generate the upload key with
   `keytool`, 4096-bit RSA, valid 30+ years, stored outside the repo.
   *Alternative if EAS is chosen: let EAS own the keystore and skip the plugin's
   signing half — but keep the debug-symbols plugin.*
2. **First signed AAB.** Add scripts:
   `build:apk` (`expo prebuild --platform android` + `assembleRelease`),
   `build:aab` (`... + bundleRelease`), `build:clean`. Keep all four ABIs for
   the bundle (Play splits per device; the old `arm64-v8a,x86_64` restriction was
   a local build-speed trick and would drop 32-bit devices).
3. **App assets.** 1024×1024 PNG icon, adaptive icon (foreground + background +
   monochrome for themed icons on Android 13+), and an `expo-splash-screen`
   config matching the existing `#020706` background. Verify the icon renders
   correctly under every launcher mask and at all densities.
4. **Safe areas.** `react-native-safe-area-context`; `SafeAreaProvider` at the
   root; top inset on the header, bottom inset on the scroll content and on the
   `OptionModal` sheet. Test portrait, landscape, gesture nav and 3-button nav.
5. **Export controls.** Decide: implement `exportScale`/`exportSamples` by
   rendering an offscreen Skia surface at scale with the higher sample count, or
   delete both. Recommendation: implement — high-resolution export is the feature
   users of a scope actually want, and the sliders are already on screen making
   a promise the app does not keep.
6. **Animation performance.** Move the clock out of React state — Reanimated 4
   is already installed, so `useFrameCallback` + a Skia `SkiaValue`, or reuse
   paths instead of rebuilding five per frame. Add an adaptive sample budget
   instead of a fixed 2200 × 5. Add a frame-time readout.
7. **Accessibility and targets.** `accessibilityRole` / `accessibilityLabel` /
   `accessibilityState` on sliders, swatches and segmented controls; raise
   every interactive target to ≥48 dp; confirm nothing clips at large font
   scales.
8. **Release build hardening.** Enable `enableMinifyInReleaseBuilds` and
   `enableShrinkResourcesInReleaseBuilds`; smoke-test Skia, Reanimated and
   Worklets under R8; record the AAB size and per-device download size.
9. **Dependency hygiene.** `npx expo install --fix` for the two patch drifts;
   keep `expo-doctor` at 18/18 in CI.
10. **Predictive back.** Keep the opt-out for 1.0 and add an explicit manual test
    that Back closes an open picker. File the migration as a 1.1 task.
11. **Patch drift in the model.** Add unit tests for `applyFrequencyMode`
    clamping, `formatRatio`, `cloneState` isolation, and interval mode at the
    24-semitone boundary. The model is the one thing here that is cheap to test
    and currently under-tested.

### 5.2 Phase 2 — store assets and Play Console (6–10 h, plus 14 days)

1. **Listing assets.** Icon 512×512 32-bit PNG without alpha; feature graphic
   1024×500; 4–6 phone screenshots (JPEG or 24-bit PNG, 16:9 or 9:16, 320–3840 px
   long edge); tablet screenshots only if landscape/tablet support is genuinely
   finished.
2. **Listing copy.** Title ≤30 chars, short description ≤80, full description
   ≤4000, category **Music & Audio** (secondary: Tools), tags, support email,
   website.
3. **App content declarations.** Privacy policy (host the page, e.g. GitHub
   Pages); ads: no; app access: all functionality available without restrictions;
   content rating questionnaire; target audience 13+; **Data safety: no data
   collected, no data shared** — this is true today and must be revisited if
   analytics or crash reporting are ever added; government/news/financial/health:
   not applicable.
4. **Play App Signing** enrollment; decide whether Google generates the app
   signing key (recommended) or you supply one.
5. **Tracking ramp.** Internal testing (up to 100 testers) → closed testing →
   if decision 5 says the account is personal and created after 2023-11-13,
   hold a closed track with ≥12 testers opted in continuously for 14 days →
   apply for production access → staged production rollout (1% → 10% → 50% →
   100%).
6. **Pre-launch report.** Available once a release is in a testing track. It runs
   Google's own automated device tests — free QA on real hardware. Fix whatever
   it finds before production.
7. **Register the app** for Android developer verification (effective
   2026-09-30).
8. **DSA trader status** if distributing in the EU.

## 8. Critical path

```
Phase 0 identity ──> signing plugin ──> signed AAB ──> internal track
       │                                                  │
       │                                                  v
       └────> docs rewrite ──> store assets ──> closed track ──> 14 days ──> production
                                                     (12 testers)
```

The 14-day closed-test clock is the longest pole and it cannot start until there
is a signed AAB. Everything else is engineering hours. If the schedule matters,
the only real lever is starting the Play account setup and the closed test as
early as possible.
